neocord manages its own shards, including respawning them after a crash, but it does not restart itself if the manager process exits or the machine reboots. Use a process manager for that.

## What neocord does on a signal

The CLI forwards `SIGINT`, `SIGTERM` and `SIGHUP` to the process it launched. Under `neocord start`, that process is the sharding manager.

When the manager receives `SIGINT` or `SIGTERM`:

1. It logs `Received <signal>, stopping shards.` and turns off respawning.
2. It asks each shard to shut down, and waits up to five seconds for each one.
3. It kills any shard still running, then exits with code 0.

Each shard shuts down in this order:

1. Stop tasks, waiting up to five seconds for runs in progress.
2. Expire live sessions, spending up to two seconds on the final edits that disable their components.
3. Call the `dispose` function from `src/context.ts`.
4. Destroy the Discord client, log `Stopped.` and exit with code 0.

A shard killed at the five second limit does not finish these steps. Keep `dispose` short.

## Exit codes and restart loops

`neocord start` exits with the manager's exit code. If shards cannot start, the manager exits with a non-zero code after logging a `NeocordStartupError`.

<Callout kind="warn">

The manager stops respawning after a fatal login error, such as a bad token, so that it cannot loop against Discord's login endpoint. A process manager that restarts the whole command undoes that protection. Always set a restart delay and a limit, as in the examples below.

</Callout>

## systemd

The working directory must contain `neocord.config.ts` and the output of `neocord build`. The CLI loads `.env` files from the project root, or you can use `EnvironmentFile`.

```ini title="/etc/systemd/system/my-bot.service"
[Unit]
Description=my-bot Discord bot
After=network-online.target
Wants=network-online.target
StartLimitIntervalSec=300
StartLimitBurst=5

[Service]
Type=simple
User=mybot
WorkingDirectory=/srv/my-bot
ExecStart=/usr/local/bin/bun run start
Restart=on-failure
RestartSec=15
KillSignal=SIGTERM
TimeoutStopSec=20

[Install]
WantedBy=multi-user.target
```

Then enable and start it:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now my-bot
journalctl -u my-bot -f
```

Replace `/usr/local/bin/bun` with the path from `which bun`. With Node, use `ExecStart=/usr/bin/npm run start`.

## pm2

Run the bot with one instance in fork mode. Do not use cluster mode or more than one instance, because each copy would start its own manager and connect the same shards. The file must end in `.cjs` because a neocord project sets `"type": "module"`.

```js title="ecosystem.config.cjs"
module.exports = {
  apps: [
    {
      name: "my-bot",
      script: "bun",
      args: "run start",
      interpreter: "none",
      exec_mode: "fork",
      instances: 1,
      restart_delay: 15000,
      max_restarts: 5,
      kill_timeout: 20000,
    },
  ],
};
```

```bash
pm2 start ecosystem.config.cjs
pm2 logs my-bot
```

## Windows

Windows has no POSIX signals. Pressing Ctrl+C in a console sends the event to the whole console, so the CLI waits up to five seconds for the child to stop by itself before it forwards `SIGINT`. Other ways of ending the process may skip the shutdown steps above.

## Logs

neocord writes `debug` and `info` to stdout, and `warn` and `error` to stderr, with an ISO timestamp on each line. Tokens are redacted. It does not write log files, so use your process manager's log handling. Set the level with `logLevel` in the config or `NEOCORD_LOG_LEVEL` in the environment, which takes priority. The levels are `debug`, `info`, `warn`, `error` and `silent`.

## Deploys

A typical release on one machine:

```pm
install
run build
run deploy
```

Then restart the service. `neocord start` needs the bundle to exist, and tells you `Run neocord build first.` if it does not. Live sessions and cooldowns reset on restart.
