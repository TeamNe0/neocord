neocord/runtime

API reference for neocord/runtime: startBot, startManager, serializeCommands, deployCommands and validateManifest.

neocord/runtime is what the CLI generates code against. Most projects never import it, because neocord build writes the entry files for you. Use it if you need to write your own entry point.

Generated entries

neocord typegen writes the entry files to .neocord/entries. This is the generated shard.ts, where the config path depends on your project:

And manager.ts:

startBot

The entry for one process. In order, it:

  1. Validates the manifest, logs warnings and fails on errors.
  2. Resolves the token, then merges intents and partials from enabled features.
  3. Creates the client, with allowedMentions: { parse: [] } as a default that config.client can override.
  4. Creates the app context from src/context.ts.
  5. Wires interactions and events, and starts tasks on clientReady.
  6. Logs in, with a 120 second timeout, and installs handlers for SIGINT, SIGTERM, SIGHUP, the { neocord: "shutdown" } IPC message and unhandled rejections.

stop() stops taking new interactions and events, waits up to five seconds for running tasks and handlers, expires live sessions, disposes the app context and destroys the client. It is safe to call more than once.

Startup failures log one message and reject with a NeocordStartupError, so .catch works as usual. If nothing catches it, as with await startBot(...) in a generated entry, the process exits with code 1 and prints no stack trace. error.transient is true for failures worth retrying, such as a network error, and false for token, intent and config errors.

If a fatal gateway close code arrives after login, such as 4004 when the token is reset while running, the bot logs the same actionable message, stops and exits with code 1.

startManager

The production entry. It wraps discord.js ShardingManager, applies config.sharding, logs lifecycle events, supervises respawns with a backoff, and forwards SIGINT, SIGTERM, SIGHUP and the { neocord: "shutdown" } IPC message. A startup failure behaves as it does in startBot. See Failure behaviour.

The shard count comes from the shards argument, then NEOCORD_SHARD_COUNT, then sharding.totalShards, then "auto". It does not deploy commands, because it has no manifest and must not load route modules. See Sharding.

deployCommands

Throws if the manifest has validation errors or there is no token. With stateFile, it skips the request when the hash and the application are unchanged, unless force is set. With dryRun, it returns before reading state or calling Discord. See Deploying commands.

serializeCommands

Converts a manifest to the JSON that Discord's command endpoint accepts. Disabled features are left out. It throws if a command has no description or a group is missing, because Discord requires a description on every parent.

validateManifest

Returns every issue instead of throwing. neocord test, neocord build and startBot all run it. It checks:

  • Default exports carry the expected brand, and layouts, error views and loading views are functions.
  • Command names, depth, descriptions, option names, option descriptions, option counts and choices are within Discord's limits.
  • Top-level commands stay within 100, children within 25, and each context menu kind within 15.
  • Parents of subcommands have a group.ts, and no path is both a command and a parent.
  • Interaction routes match their file, do not start with ~, fit in 100 characters and do not conflict.
  • Events match their file, task intervals are between 1 ms and 2147483647 ms, and durations parse.
  • With config, events have the intents they need, and Guilds is enabled.

NeocordStartupError

The error for startup failures, with an actionable message. Its stack is only the name and message, so logs stay readable. The original error is on cause when there is one. See Troubleshooting for the messages.
