Live sessions

Stateful messages with onClick, onSelect and useState, and how TTL, process limits and restarts behave.

Put onClick on a button or onSelect on a select and the message becomes a live session. The React tree stays mounted in memory, so useState and effects work as they do on the web, and you do not need a route file for the component.

This preview runs the same logic, so its buttons work:

When to use one

Use a live session forUse a route file for
Short-lived UI: pagination, wizards, confirmations, games.Buttons that must keep working after a restart or days later.
State that does not need to survive.Anything that needs a cooldown, or permissions and middleware of its own.

You can mix them. A tree can hold onClick buttons and route buttons at once.

How a click is handled

  1. neocord renders your node through a live root. If the committed tree has any handler, the session is stored.
  2. Each live component gets a custom id of the form ~<sessionId>:<index>. The ~ prefix is reserved, so your own custom ids cannot start with it.
  3. A click re-checks the route that opened the session, as the warning below describes, then dispatches to the handler for that id. It waits for an async handler to finish.
  4. If the handler did not acknowledge the interaction, neocord updates the message with the latest render.

Ids follow React's identity rules: a component keeps its id across re-renders for as long as its position and key stay the same. So a click on the current message always reaches the newest closure.

Clicks on one session run one at a time, in the order they arrive, so a double click on an async handler runs it twice in sequence and keeps both state updates. Different sessions do not wait for each other.

The autoDefer timer also runs during a click, including while a click waits for the one before it, and defers the update if your handler is slow.

The handler argument

The handler receives the discord.js interaction. You can read from it, or respond through it, and neocord then edits the message without responding again.

A slow handler can outlast autoDefer, which acknowledges the click for you. The event's response methods keep working when that happens, so the same handler works however long it takes:

Call after the automatic deferWhat neocord does
event.reply(options)Sends it as a follow-up, which resolves to a Message. An ephemeral flag still applies.
event.update(options)Edits the message with editReply.
event.deferUpdate()Nothing, because the click is already acknowledged.
event.deferReply(options)Nothing yet. The next event.editReply sends a new message, and later ones edit that message. event.deleteReply deletes it.
event.showModal(modal)Throws an error that names autoDefer, because a modal must be the first response. The route's error view shows it.

Before the automatic defer, these methods behave as they do in discord.js. Open a modal before any slow work.

useLiveInteraction() returns the current event in components that render during a dispatch, and null otherwise.

ctx.showModal cannot open a modal from a click, because ctx is bound to the interaction that created the session, which has already been answered. Use the event: event.showModal(renderModal(...)).

/Warning

Every click re-checks the guildOnly and permissions of the route that opened the session, then runs its middleware with ctx.kind set to "button" or "select". Middleware limited with kinds: ["command"] does not run for clicks, and cooldown is not applied to them.

Past those checks, anyone who can see the message can click, not only the person who ran the command. Compare event.user.id with the original user when that matters, or make the message ephemeral.

Updates outside a click

A state change from anything else also edits the message, such as a timer or a promise.

Edits are coalesced: one edit runs at a time, and only the newest pending payload is sent. Intermediate states can be skipped under load. Discord rate limits still apply, so do not update more often than you need. A tree needs at least one handler for a session to exist, and without one it is unmounted right after sending.

Replacing the message

A message shows one thing at a time, so a new delivery to the message ends the session on it. The tree unmounts, its effect cleanups run, and neither a timer nor the TTL can edit the message again.

What replaces the messageExample
Editing the reply through the same ctxawait ctx.reply(<Confirm />), then await ctx.editReply(<Banned />).
A route button or select that updatesA route button in the same tree that returns a node.
A modal with respond: "update" opened from the messagesubmit returns a node.
Deleting the replyawait ctx.deleteReply().

A follow-up, or a route with respond: "reply", sends a new message and leaves the session running. So does a route that returns nothing. A response made directly on a raw interaction, such as ctx.interaction.update(...) or ctx.message.edit(...), is not tracked, so the session keeps running and can overwrite it.

TTL

A session has an idle timeout, set by live.ttl.

FactDetail
Default14m
Accepted valuesA duration string, such as "5m" or "1h30m", or a number of milliseconds, from 1ms to 2147483647ms (about 24.8 days). Anything else is a validateManifest error, which also fails startup.
What resets itEach click on the session. A timer calling setState does not.
When it passesThe message is edited one last time with every button and select disabled, then the tree unmounts and effect cleanups run.

The default sits under Discord's 15 minute lifetime for interaction tokens, which is what neocord edits through. The initial token is replaced by each click's, unless the handler answered that click with a reply of its own. A click late in a token's life also extends the TTL past it, and so can a longer ttl, so edits on an idle session can fail once the token expires. After at least one click of any kind, neocord falls back to editing through the message. Otherwise it logs a warning, and the components stay enabled on the message. Ephemeral messages cannot be edited through the message, so they keep their components in that case too.

Per-process limits

Sessions live in a Map in the process that created them.

  • They are not persisted or shared. There is no database or Redis option.
  • With sharding, each shard has its own store. Discord sends a guild's interactions to the shard that owns the guild, so clicks reach the shard holding the session, as long as the shard count does not change.
  • Each open session keeps a React tree and its closures in memory until it expires. neocord sets no limit on the number of sessions, so a command that many people run all day can hold many trees. Lower live.ttl if that matters.

Restart behaviour

EventResult
Graceful stop (SIGINT, SIGTERM, manager shutdown)neocord tries to expire every session, so their components are disabled. It waits up to two seconds for those edits, then unmounts the rest.
Crash or killNothing runs, so messages keep their enabled buttons.
A click after eitherThe session is gone, so neocord removes the live components from the message and sends an ephemeral "This message has expired." notice. Route buttons, route selects and link buttons stay, and rows or containers left empty are removed. If that would leave the message empty, only the notice is sent.

The handler code does not run again. If users need a button to work after a deploy, use a route file and put the state in its params or your database.

neocord dev restarts the bot on every change, so live messages expire often in development.

Errors

A throw in a handler is logged, and the route's error view is sent as an ephemeral message. The session stays open and a later click can succeed. A render error from a background update is logged as "A live session failed while updating."

What cannot be live

onClick and onSelect throw outside a live root, with a message that names the fix. That covers:

  • Modals.
  • Error views and other one-shot renders from render or renderAsync.

Testing

Pass live: true to a run helper to keep the session open. The result then has a live object with click(label) and select(values), and each resolves to a result with the updated text. Call live.close() when the test is done. See Testing live sessions.
